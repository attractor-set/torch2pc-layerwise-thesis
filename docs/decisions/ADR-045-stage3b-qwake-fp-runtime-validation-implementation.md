# ADR-045: реализация допуска и оркестрации `QW-4B` для проверки среды выполнения

[English version](ADR-045-stage3b-qwake-fp-runtime-validation-implementation_EN.md)

- **Статус:** принято как `QW-4B-I`; [запуск](../glossary.md#term-run) и создание [доказательных материалов](../glossary.md#term-evidence) остаются закрытыми
- **Дата:** 2026-07-24

```text
qwake_fp_runtime_validation_implementation_complete=true
qwake_fp_runtime_preflight_implemented=true
qwake_fp_runtime_authorization_validator_implemented=true
qwake_fp_runtime_adapter_symbols_bound=true
qwake_fp_matched_runtime_runner_implemented=true
qwake_fp_runtime_report_sealer_implemented=true
qwake_fp_canonical_torch_backend_implemented=true
qwake_fp_all_snapshot_observer_implemented=true
qwake_fp_authorized_execution_cli_implemented=true
qwake_fp_static_validation_receipt_chain_implemented=true
qwake_fp_runtime_authorization_issued=false
qwake_fp_runtime_validation_performed=false
qwake_fp_pre_freeze_evidence_generated=false
qwake_fp_pre_freeze_validation_complete=false
qwake_fp_live_adapters_bound=false

qwake_fp_next_stage=QW-4-runtime-validation
qwake_fp_next_slice=QW-4-runtime-freeze
```

## Контекст

`QW-4A` заморозил запрос, пары `P0/P1/P2`, поля равенства, счётчики
отключённых эффектов, изоляцию оракула и обязательные линии CPU и ROCm. Для
реальной инженерной проверки требовалась отдельная реализация
[среды выполнения](../glossary.md#term-runtime), которая не смешивает три
различных действия:

1. проверку среды и исходного кода;
2. выпуск разрешения на одну попытку;
3. [выполнение](../glossary.md#term-execution) проверки и сохранение её результатов.

Если реализация сама выпускает разрешение или автоматически открывает
вычисление, граница закрытия при ошибке исчезает. Поэтому `QW-4B` разделяется
на реализацию, заморозку допуска и отдельное получение инженерных материалов.

## Решение

### 1. Предварительная проверка без вычисления модели

Добавляется `stage3b_qwake_fp_runtime.py`, который строит и повторно проверяет
`stage3b-qwake-fp-runtime-preflight-v1`. Предварительная проверка связывает:

- чистый `source_commit` и канонический хеш индекса Git;
- чистый коммит Torch2PC;
- неизменяемый хеш образа;
- SHA-256 запроса `QW-4A` и контракта `QW-2`;
- хеш закрытого реестра символов адаптеров;
- идентичности Python, PyTorch, HIP и устройства для обеих линий;
- упорядоченную пару `CPU/float64`, затем `ROCm/float32` одного образа.

На этом шаге все разрешения запрещены по умолчанию, запуск не открывается.

### 2. Отдельная схема разрешения

Реализация содержит только валидатор будущего
`stage3b-qwake-fp-runtime-authorization-v1`. Она не создаёт и не подписывает
пакет разрешения. Валидатор требует:

- точный хеш предварительной проверки;
- ту же идентичность исходного кода, образа и Torch2PC;
- полный, но строго инженерный набор разрешений;
- SHA-256 квитанции завершённых статических и модульных проверок и цепочку, связывающую её с точной предварительной проверкой;
- пары `P0/P1/P2` на каждой линии CPU и ROCm;
- один относительный и ещё не существующий каталог результатов;
- ровно одну попытку;
- точное подтверждение оператора;
- закрытые научные, тестовые, публикационные и образные барьеры.

Доступ к подтверждающим данным, выбор политики и публикация в этот набор не
входят.

### 3. Локальная граница адаптеров

Модуль `stage3b_qwake_fp_runtime_adapter.py` реализует ровно символы,
замороженные запросом `QW-4A`:

```text
collect_A0
collect_A1
collect_A2
run_registered_analytics
compute_post_action_oracle
record_edge_costs
```

Каждая функция проверяет своё разрешение непосредственно перед эффектом.
Модуль не импортирует PyTorch или Torch2PC при загрузке и принимает только
объект вычислительной основы из разрешённой сессии среды выполнения. `A0` остаётся
структурным и не может читать тензоры, выделять временную память,
синхронизировать устройство или выполнять передачу на узел.

Конкретная вычислительная основа `stage3b_qwake_fp_runtime_torch.py` уже входит
в этот срез реализации. Она жёстко связывает `lenet_classic`, исправленный
`stage2_baseline` `FixedPred`, `eta=1`, зарегистрированное число итераций и
детерминированный синтетический инженерный пакет. Для наблюдаемой ветви она
использует эквивалентную копию замороженного исправленного цикла FixedPred с
обратным вызовом только для чтения на снимках `0..K`; эталонная ветвь вызывает
исходную функцию из закреплённого Torch2PC. Именно пары `P0/P1/P2` позже
проверяют, что обратный вызов не меняет конечную точку, градиенты, состояния,
функцию потерь, последовательность переходов или состояние генераторов.

### 4. Сопоставленный исполнитель

Для каждой клетки исполнитель один раз сохраняет состояние модели,
оптимизатора и всех генераторов случайных чисел. Перед каждой ветвью состояние
и генераторы восстанавливаются. Ветви выполняются последовательно в одном из
двух зарегистрированных порядков:

```text
reference -> instrumented
instrumented -> reference
```

Исполнитель проверяет наличие клетки в разрешении, хеши состояния и
генераторов, линию, [случайное начальное значение модели](../glossary.md#term-model-seed), пакет и идентичность
пары. После этого применяются чистые средства сравнения `QW-4A`. Одновременный
запуск двух ветвей запрещён.

### 5. Двухлинейный инженерный отчёт

Отчёт обязан содержать `P0/P1/P2` для CPU и ROCm, вложенность каждой линии,
отрицательные проверки разрешений, изоляцию оракула и барьеры целостности,
квитанций и статических тестов. Результаты пар ROCm проецируются в исходный
`PreFreezeValidationReport`, но отчёты CPU и ROCm сохраняются отдельно.

Граница отчёта:

```text
engineering_evidence_only=true
scientific_evidence=false
publication_permitted=false
```

Чистая функция запечатывания возвращает канонический `JSON` и SHA-256, но сама
не записывает файлы.

### 6. Граница командных программ

Добавляются три служебные команды:

- `preflight_stage3b_qwake_fp_runtime.py` строит или проверяет предварительный
  отчёт среды;
- `verify_stage3b_qwake_fp_runtime_authorization.py` проверяет будущий пакет,
  квитанцию статической проверки и открывает только инженерную сессию в памяти;
- `run_stage3b_qwake_fp_runtime_validation.py` является единственной
  исполняющей командой и вызывает FixedPred только после успешной проверки
  предварительной проверки, разрешения, цепочки квитанций, идентичностей
  исходного кода, образа и Torch2PC, а также отсутствующего каталога
  результатов. Она атомарно сохраняет только инженерный отчёт и никогда не
  открывает научные [доказательные материалы](../glossary.md#term-evidence) или публикацию.

Ни одна команда не выпускает разрешение. Команды предварительной проверки и
проверки разрешения не вызывают FixedPred; исполняющая команда без внешнего
замороженного разрешения закрывается с ошибкой.

## Граница реализации

Этот срез завершает только `QW-4B-I`. Он не содержит:

- замороженного предварительного отчёта или пакета разрешения;
- случайных начальных значений модели, пакетов данных или каталога результатов;
- фактического выполнения CPU или ROCm и выпущенного разрешения;
- файлов инженерного отчёта;
- права создавать научные оракульные метки;
- разрешения на `QW-5` или кампании `C1/C2/C3/R`.

Следующий срез `QW-4B-F` должен заморозить фактическую предварительную проверку,
точные клетки, идентичности образа, исходного кода и Torch2PC, а также
разрешение на одну попытку. Только после его слияния допускается отдельный
`QW-4B-E` для получения инженерных материалов.

## Последствия

Успешная проверка этой реализации означает только машинную проверяемость
допуска, последовательного выполнения и запечатывания. Она не подтверждает
отсутствие возмущения на реальном оборудовании. До успешного запечатанного
отчёта обеих линий `qwake_fp_scientific_image_freeze_permitted=false`.
