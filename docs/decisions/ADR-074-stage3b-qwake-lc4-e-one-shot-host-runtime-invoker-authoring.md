# ADR-074: авторинг одноразового хостового исполнителя `QW-LC4-E`

- Статус: принят для отдельного среза разработки контракта
- Дата: 2026-07-29
- Базовый коммит: `be6486a9e3670343132f2c863a5a0cd5969ee9f6`
- Связанные решения: ADR-067, ADR-070, ADR-071, ADR-072, ADR-073

## Контекст

PR №134 материализовал проверку точного локального образа и канонический
`argv` будущего контейнерного вызова. Хостовый исполнитель всё ещё отсутствует.
Следующий контракт должен определить единственную допустимую траекторию от
наблюдательной проверки до [выполнения](../glossary.md#term-execution), не
открывая её в ветке разработки контракта.

Существующая одноразовая точка входа атомарно захватывает файл владения внутри
контейнера и выполняет вычислительный модуль в том же процессе. Поэтому хост не
может предварительно записывать файл владения: это нарушило бы уже
зафиксированное требование `claim-and-execute-same-process`.

## Решение

Вводится чистый контракт
`stage3b-qwake-lc4-e-one-shot-host-runtime-invoker-contract-v1`.
Он связывает коммит слияния PR №134, пакет реализации обёртки, разрешение
одноразового вызова, точный образ, точку входа и атомарную реализацию файла
владения.

Контракт фиксирует следующую траекторию:

1. повторная проверка неиспользованного разрешения и отсутствия эффектов;
2. `docker image inspect` точного `image repo digest`;
3. материализация канонического `argv` только в памяти;
4. непосредственная повторная проверка образа, `argv`, файла владения, результата
   и временного дерева;
5. ровно один [запуск](../glossary.md#term-run) дочернего контейнерного процесса через точный `argv`, без
   интерпретации оболочкой;
6. атомарный захват файл владения контейнерной точкой входа;
7. повторная проверка сохранённого файла владения и замороженного допуска после захвата;
8. вызов ограниченного вычислительного модуля и продвижение полного результата
   без замены существующего пути;
9. терминальная классификация кода возврата, тайм-аута или сигнала без
   автоматического повтора.

Хосту запрещено записывать файл владения. Граница потребления разрешения —
успешный атомарный захват файла владения внутри того же контейнерного процесса, который
затем выполняет вычислительный модуль. После появления файла владения он сохраняется при
любой ошибке, и повтор запрещён.

## Управление процессом

Будущая реализация обязана:

- передавать только массив аргументов и использовать `shell=false`;
- запускать не более одного дочернего процесса на один вызов исполнителя;
- не наследовать произвольное окружение и не переопределять рабочий каталог;
- создать отдельную группу процессов;
- пересылать `SIGINT` и `SIGTERM` дочерней группе;
- применять тайм-аут 7200 секунд и 30-секундный период мягкого завершения;
- ограничить захват `stdout` и `stderr` одним MiB на поток;
- считать ненулевой код, тайм-аут и сигнал терминальным исходом;
- не сохранять `argv` или отдельные хостовые журналы;
- не выполнять автоматический повтор после попытки запуска дочернего процесса.

Атомарный файл владения остаётся межпроцессным арбитром: конкурирующие контейнеры не
могут оба перейти к вычислению. Гарантия устойчивой к сбоям одноразовости начинается с
успешного захвата сохраняемого файла владения. До этой границы отказ не считается
потреблением разрешения, но один экземпляр хостового исполнителя всё равно не
может выполнить второй запуск.

## Граница среза разработки контракта

Этот срез содержит только типизированный контракт данных, проверяющую программу, замороженный
реестр, тесты и двуязычную документацию. Он не импортирует `subprocess`,
вычислительный модуль, реализацию исполняющей обёртки или реализацию

## Последствия

После слияния контракта можно открыть отдельную ветку реализации. Она должна
реализовать процессный контроль и единственный запуск контейнера, но не должна
запускать реальную [среду выполнения](../glossary.md#term-runtime) в ходе
разработки или тестов. Фактический одноразовый вызов останется отдельной
операцией после независимой проверки реализации.
