# ADR-118: реализация хостового механизма создания процесса для попытки 003

## Статус

Принято как ограниченный срез реализации. Базовый коммит:
`34ec64823bff556706190c2f2c93b3a0653e293d`; базовое дерево:
`b851597ba271cea6e0b2e5868a654cf5b52b43f2`.

## Контекст

PR #187 слит в `main`. Авторитетная хост-команда уже материализована и затем
независимо реконструирована побайтно. Зафиксированы:

- `claimed_at_utc=2026-08-10T14:47:42Z`;
- `invocation_sha256=sha256:91e762ba21c1d72b9282a3b0419206d5de1c3f88aac82a63dad76e27f0321c24`;
- `command_record_sha256=sha256:3ea2d34826fdd5846eee7cdfa84833f6b5e2293cfef76b76a51b64862cb143ca`;
- физический SHA-256 записи команды
  `f519d0821305171aa5c6ed05cad772f9fd85e93601fa1ec551e23058939d1ba6`.

Запись команды является единственным допустимым источником будущего создания
хостового процесса. Авторизация не потреблена,
[попытка](../glossary.md#term-attempt) 003 не начата, аренда
[выполнения](../glossary.md#term-execution), вывод
[среды выполнения](../glossary.md#term-runtime) и хостовый итог отсутствуют.

## Решение

Реализовать ограниченный хостовый механизм создания процесса непосредственно в
этом срезе, без дополнительного промежуточного PR только с контрактом.

Механизм обязан:

1. непосредственно перед созданием процесса повторно проверить физический и
   семантический SHA записи команды;
2. использовать только сохранённый точный `argv`;
3. выполнить ровно один `subprocess.Popen`;
4. использовать `shell=False`;
5. использовать фиксированное хостовое окружение `LANG=C`, `LC_ALL=C` и
   фиксированный `PATH`, не наследуя произвольное окружение хоста;
6. использовать корень выполнения как `cwd`;
7. создать отдельную группу процессов через `start_new_session=True`;
8. закрыть лишние файловые дескрипторы через `close_fds=True`;
9. пересылать `SIGINT` и `SIGTERM` группе дочернего процесса;
10. ограничить работу 7200 секундами и дать 30 секунд на штатное завершение;
11. ограничить захват `stdout` и `stderr` одним МиБ каждый;
12. не выполнять автоматическую повторную попытку.

Реализация возвращает терминальный хостовый итог в память, но сама его не
сохраняет. Проверка репозитория и тесты не выполняют реальное создание процесса:
вместо него внедряется фиктивный адаптер.

Хост не создаёт аренду выполнения и не потребляет авторизацию. Эти переходы
по-прежнему принадлежат
`container_entrypoint_atomic_execution_lease` внутри запущенного контейнера.

## Граница среза

После слияния реализация существует и технически способна выполнить точную
сохранённую команду Docker, но само [выполнение](../glossary.md#term-execution) остаётся закрытым до
отдельного явного одноразового действия оператора.

```text
AUTHORITATIVE_HOST_COMMAND_MATERIALIZED=true
COMMAND_PERSISTED=true
PROCESS_SPAWNER_CONTRACT_PRESENT=true
HOST_PROCESS_SPAWNER_PRESENT=true
HOST_PROCESS_SPAWNER_EXECUTABLE=true
HOST_PROCESS_SPAWNED=false
DOCKER_RUN_IMPLEMENTED=true
DOCKER_RUN_INVOKED=false
AUTHORIZATION_USED=false
AUTHORIZATION_CONSUMED=false
ATTEMPT_STARTED=false
EXECUTION_LEASE_MATERIALIZED=false
RUNTIME_EXECUTION_PERMITTED=false
RUNTIME_EXECUTION_STARTED=false
RUNTIME_EXECUTION_PERFORMED=false
MODEL_CODE_INVOKED=false
DATASET_ACCESSED=false
```

## Следующий переход

После CI, слияния и проверки состояния после слияния остаётся один
содержательный переход: явный одноразовый
[запуск](../glossary.md#term-run). Он повторно проверяет точную запись команды
и отсутствие аренды и вывода, затем один раз вызывает уже слитый
`spawn_attempt_003_persisted_command()`. После создания хостового процесса
право атомарно захватить аренду и потребить авторизацию остаётся у точки входа
контейнера.
